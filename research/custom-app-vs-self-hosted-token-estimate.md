# 銷售儀表板：AI GO Custom App 與直接部署的 Token 概算

> 更新日期：2026-11-04（Asia/Taipei）｜文件性質：工程預算與匿名歷史用量分析，非配對實測。
> [公開文件索引](../README.md) · [匿名用量與計量方法](token-estimate-evidence.md)

依本比較「兩邊都從零設定資料、登入、權限與上線」的前提，將直接開發並部署至一般 VM／容器主機的完整 Token 設為 **100**，AI GO internal Custom App 可先編列 **約 75–80**，保守工程估算帶為 **65–90**，也就是約少 **10–35%**。這個比例包含計畫、討論、Skill、程式開發、測試修復、部署腳本、CI 與正式站驗證；Custom 從空白 internal App 開始，不使用市集業務模板。這是工作拆解得到的預算，**不是同條件配對實測結果，也不是統計信賴區間**。匿名歷史紀錄可確認用量量級及快取的重要性，但目前選取的案例沒有同功能、同模型、從零到上線的對照組。額外載入平台文件、長期保留大上下文或反覆處理平台限制，能把 AI GO 的完整 Token 推近、甚至推高於直接開發。以下比例適合首次交付的初步預算，不能直接換算成 API 金額、訂閱額度或開發工時。

比較固定為有登入的內部銷售儀表板：4–6 個 KPI、趨勢與分類圖、日期／人員篩選、可排序分頁明細、CSV 匯入匯出、手機與桌機版、錯誤及空狀態、主管與業務兩種角色。兩邊使用相同合成資料，從空資料開始，都要驗證指標、退款取消、時區、重複匯入與伺服端資料權限，最後由非開發者帳號驗收 HTTPS 正式網址。平台帳號或一般主機帳號已可使用，但 App 與交付所需配置尚未建立。直接開發可使用成熟框架及登入套件，無須自行發明密碼技術。

AI GO 的空白腳手架沒有銷售儀表板業務功能，因此圖表、畫面及指標邏輯仍須開發。平台既有身分、資料 API 與發布工具減少的是底層工程；帳號邀請、角色、資料匯入、聚合 Action 與資料授權仍要配置及驗證。App 可見度也不能代替資料授權。([空白腳手架](https://github.com/AI-GO-APP/aigo-app-builder-skill/blob/57b1fbc4f37402211714779135a14f7a9cb88a3e/scripts/aigo_scaffold.py)、[成員與授權規則](https://github.com/AI-GO-APP/aigo-app-builder-skill/blob/57b1fbc4f37402211714779135a14f7a9cb88a3e/references/member-admin.md))

下面以直接開發的總額為 100，列出一個透明的中央預算。各列都是概算單位，不是測得的階段 Token。若某列為 10，表示占直接開發總預算的十分之一，不表示該階段只消耗 10 Token。

| 階段 | 直接開發 | AI GO Custom | Custom／直接 | 差異的主要來源 |
|---|---:|---:|---:|---|
| Skill／文件學習與查證 | 8 | 10 | 125% | 平台規格較多；直接開發的框架、資料庫、登入與主機文件也有計入 |
| 計畫／構思 | 10 | 9 | 90% | KPI、頁面、權限與驗收相同；減少部分技術與部署拓撲選型 |
| 使用者討論 | 6 | 6 | 100% | 保持相同的需求與視覺決策品質 |
| 執行協調 | 5 | 4 | 80% | 查檔、環境檢查、命令安排及結果判讀；不重算寫程式及部署 |
| 前端業務開發 | 23 | 23 | 100% | 從空白 App 起手，圖表、篩選、明細與 RWD 都要做 |
| 資料／後端／登入權限 | 20 | 8 | 40% | 平台提供底層資料與身分原語；仍計入模型映射、匯入、Actions 與授權 |
| 測試／修復 | 12 | 10 | 83% | 相同業務、畫面與權限驗證；減少部分自行管理服務的整合測試 |
| 部署，含部署腳本與正式驗證 | 10 | 3 | 30% | 重用平台發布器；直接開發需編寫及排查主機、服務、TLS、部署與回滾機制 |
| CI／Git／PR 交付 | 6 | 3 | 50% | 兩邊都有測試、版本保存與 PR；差額主要為新增部署 workflow 及相關排查 |
| **合計** | **100** | **76** | **76%** | **示範預算：少 24%，宜表述為約省四分之一** |

每次模型請求只依主要目的歸入一列，該次的完整歷史及工具結果一起計入。例如讀完 Skill 後進行開發，後續攜帶的 Skill 上下文已包含在開發列，不能再重複加到 Skill 列。「思考」則是各階段輸出的一部分，不另建立一列加回。這張表的最大不確定來源是各階段實際請求數與平均上下文，故 **76 不應被解讀成精確到個位數的測量**。

本比較採用的 Custom 發布流程為本機 sync、型別／編譯檢查、publish、回讀及正式網址驗證，再開 PR 並 squash merge 保存程式。不為 Custom 建部署 Actions，但仍可有 lint、測試與建置驗證 CI。直接開發的部署列包括 Dockerfile／runtime、服務設定、環境變數、反向代理／TLS、部署腳本與健康及回滾檢查；CI 列則計部署 workflow、secrets 指向、併發與失敗排查，兩列不重算同一份腳本。([Custom 發布工具與驗證](https://github.com/AI-GO-APP/aigo-app-builder-skill/blob/57b1fbc4f37402211714779135a14f7a9cb88a3e/SKILL.md))

輪數必須分清楚。人類討論回合、模型請求次數、工具呼叫次數不是同一件事；一個使用者回合內可以出現數十次模型與工具迴圈。公平比較固定功能、模型、推理強度及討論方式，讓模型請求數成為結果；若把兩邊請求數硬設相同，就無法衡量平台減少工程迴圈的效益。

| 輪數／批次 | AI GO Custom | 直接 VM／容器 | 性質 |
|---|---:|---:|---|
| 需求與設計的人類討論 | 同樣 6 輪 | 同樣 6 輪 | 示例控制條件，非歷史觀察 |
| 核心 UI／資料功能迭代 | 3–5 批 | 3–5 批 | 事前規劃假設 |
| 身分／資料層整合 | 1–3 批 | 3–6 批 | 平台減少底層整合工作 |
| 部署／CI／正式驗證 | 1–3 批 | 3–6 批 | 直接開發包含部署機制建立 |

這些批次可能在同一個人類回合完成，不能直接加成總回合或模型請求數。CI runner 自己執行十分鐘、主機自行建置或等待部署完成，不會因等待時間自動產生模型 Token；模型讀日誌、判斷狀態及修錯的請求才會產生用量。

**完整 Token 要包含快取讀取。** OpenAI 的 cached input 已包含於 input，reasoning 已包含於 output，因此每次只加 input＋output。Anthropic 的完整輸入則要加未快取 input、cache creation 與 cache read，再加 output；thinking 也不能額外重加。模型指令、工具規格、歷史、檔案與工具結果都屬輸入，不能只算最後生成的程式碼。([OpenAI 用量規則](https://developers.openai.com/api/docs/guides/agents-api/observability)、[Claude 快取欄位](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Claude 思考用量](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost))

Skill 也不是只計一次檔案大小。2026-11-04 研究時量得 aigo-builder 主檔為 **24,575 字元**；依中英文混合字元粗估約 **1.2–1.7 萬 Token**。主檔加六份選定規劃及開發參考若整份讀取，粗估約 **3.3–4.8 萬 Token**。這不是實際 tokenizer 計數，也不是每次必然載入量。Skill 先提供名稱與描述，正文及 references 按需載入；未讀的檔案不能算成上下文。([公開 Skill 規格](https://github.com/AI-GO-APP/aigo-app-builder-skill/blob/57b1fbc4f37402211714779135a14f7a9cb88a3e/SKILL.md)、[OpenAI Skill 載入方式](https://learn.chatgpt.com/docs/build-skills)、[Claude Skill 載入方式](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview))

真正要估的是額外上下文保留多久。例如 AI GO 比直接開發多讀 **20k Token**，後續 **80 次**請求都保留這段內容，就增加約 **1.6M 完整輸入 Token**。這只是敏感度例子，不能再疊加到已包含完整上下文的階段表。快取能改變這段輸入的費率，不能令完整 Token 變成零；壓縮或分拆 Session 會改變後續的輸入量。([OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Claude Code 用量說明](https://code.claude.com/docs/en/costs))

將完整 Token 換成絕對數字，至少要有「模型請求數 × 每次平均完整輸入與輸出」。以下是獨立的算式示範，並非上表的實績，也不是本案絕對預測：

| 示例參數 | 直接開發 | AI GO Custom |
|---|---:|---:|
| 模型請求數 | 120 | 80 |
| 每次平均 input＋output，含快取讀取 | 80k | 100k |
| 完整 Token | 9.6M | 8.0M |
| AI GO／直接開發 | — | **83%，少 17%** |

此例中，AI GO 請求少三分之一，但平均上下文大四分之一，所以完整 Token 只少約六分之一。如果 AI GO 的每次平均用量升至 120k，同樣 80 次就達 9.6M，完整 Token 節省消失。這比單純比較程式碼行數更能說明 Skill、規格探索與輪數的交互影響。

本次從原生 Claude Code JSONL 與 Codex rollout 的 usage 欄位取樣，依唯一 message／response ID 去重，排除只有匯入歷史快照、無法證明新請求用量的紀錄。下表為實際歷史用量量級；「排除快取讀取」仍包含 cache creation 與 output，不能當成費用。

| 原生 Claude Code 案例 | 模型請求數 | 完整 Token | 排除快取讀取 | 平均完整輸入／次 | 快取讀取占輸入 |
|---|---:|---:|---:|---:|---:|
| 業務分頁增修，樣本 A | 135 | 38.099M | 0.460M | 281k | 99.11% |
| Custom App VFS／本地同步，樣本 B | 33 | 3.965M | 0.104M | 120k | 97.72% |
| 既有官網改版並上線，樣本 C | 119 | 30.474M | 0.544M | 255k | 98.67% |

前兩例的原始紀錄包含 builder API、VFS、compile 與 publish，可確認為 AI GO Custom App；官網案例則記錄 Zeabur 監看 main、PR 合併、主機自動部署成功與正式網址／資產檢查，可確認為直接主機部署。這些只是歷史執行證據，本研究沒有重新驗證目前正式站狀態。官網本身已有主機與部署機制，沒有從零建立資料庫、登入或 CI；前兩例也是既有系統的增修及同步。部分案例跨模型，Session 還可能包含需求延伸、歷史背景與分支／子代理，因此以上只能支援「長 Session 的完整 Token 可達數千萬，而多數為快取重讀」這個量級判斷。**不能把 38.099M 除以 30.474M，當成平台節省或多耗多少的證據。** 原始使用者訊息數也不等於純粹人類決策輪數，因為紀錄可能包含延續或系統注入訊息；單一 Session 用量也不保證涵蓋所有子代理或其他工作階段。([匿名取樣證據與去重方法](token-estimate-evidence.md))

目前選樣沒有足夠資料分別建立可信的「Codex AI GO／Codex 直接開發」與「Claude Code AI GO／Claude Code 直接開發」實測比例。兩者 tokenizer、模型行為、推理與快取策略不同，不能把一邊的 AI GO 任務與另一邊的直接開發任務相除。正式量測應固定各工具內的模型、effort、Skill 讀取及壓縮策略，用同一份需求、合成資料與驗收檔，各自完成並累計全部必要請求、失敗重試與子代理；再報各工具內的中位數與範圍。本次為分析而消耗的研究 Token 不列入被比較的開發預算。

「直接上主機」也包括管理式平台，不能一律假定自行管理 VM。即使從空資料及新 App 開始，直接開發仍可合法採用成熟 auth／BaaS、starter 與一鍵 PaaS；若部署腳本、登入和權限整合已有可重用基礎，大部分額外工項會消失，AI GO 比例就會靠近 1，規格探索較重時也能超過 1。因此 **65–90% 的主估區間限於還需要建立一般 VM／容器部署機制的情境**，不能直接套給 Vercel／Zeabur 等成熟整合架構。反過來，若 AI GO 已有真實銷售資料、直接開發卻還得另做整套資料接入，差距會擴大，但那是既有資料資產造成的額外效益，不符合本題兩邊從零的前提。特殊 SSO、自有網域、複雜即時通訊、大型分析或平台不支援的框架，也不宜套用上述範圍。([Custom 能力邊界](https://github.com/AI-GO-APP/aigo-app-builder-skill/blob/57b1fbc4f37402211714779135a14f7a9cb88a3e/references/product-line-decision.md))

實務編列可先以 **直接開發 1：AI GO 0.8** 作為本題首次交付的完整 Token 預算，保留 **0.65–0.90** 的情境範圍，再用前幾個里程碑的實際請求數與平均上下文修正。預期差額主要來自後端／登入設施、部署腳本與部署 CI；需求討論、前端和資料正確性不應承諾相同比例的節省。若要談費用或訂閱額度，須另依指定模型、方案與各類 Token 計價，不能沿用這個比例。


## 公開版來源與維護

本文件於 2026-11-04 整理為公開版。歷史案例只保留匿名彙總；原始開發 Session、提示、工具輸出、客戶／租戶識別資訊、帳密與本機路徑不公開。因此公開讀者可以重算表內數字與示例，但無法僅靠此 repo 獨立重播原始歷史案件。

平台能力與腳手架的來源連至公開 aigo-app-builder-skill 固定版本 `57b1fbc4f37402211714779135a14f7a9cb88a3e`。Skill 字元數與 Token 粗估則是研究時本地副本的觀察值，不保證與該公開版本逐字一致，也不代表未來版本的上下文成本。

修改概算時，須重新檢查功能、資料起點、登入、權限、部署方式、CI、模型與推理強度是否一致；沒有同條件配對實驗前，維持「工程概算」標示。
